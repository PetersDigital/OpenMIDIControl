## v0.5.0 MCU controls and high-resolution transport

1. A Galaxy running OpenMIDIControl can operate eight Cubase mixer strips and the master from the **MCU 8-Track Mixer** template. Faders touch, write and release automation. V-Pots send relative movement. Strip buttons and the existing nine header buttons operate the host and display its feedback.
2. Generic MIDI can exchange 32-bit Pitch Bend and ordinary absolute CC values on a MIDI 2.0 route. On a byte-stream route the app sends ordinary MIDI 1.0 bytes, with 14 bits for Pitch Bend and 7 bits for an ordinary CC. Existing explicitly paired 14-bit CC bindings retain their MSB/LSB behavior.
3. Existing layouts, Generic MIDI assignments, Aftertouch and Latch Pads, and page-switch release behavior survive upgrade. Keep layout schema v2. Use an explicit Generic/MCU mode for this milestone. Automatic discovery, MCU handshake, HUI heartbeat and SysEx7 belong to v0.5.1. LCD, meter, V-Pot ring and bank-display feedback belong to v0.5.2. Host scripts belong to v0.6.0.

**Gate 0 passed.** The operator confirmed that Cubase 15.0.40.324 (WinRT) and 16.0.5.174 (Windows MIDI Services loopback) accepted track 1 touch/move/release and Play/Stop immediately. v0.5.0 can start with the transport decoder. MCU handshake remains in v0.5.1.

**Packet contract.** Follow M2-104 Table 4 for all sixteen MT lengths in 32-bit words: `1,1,1,2,2,4,1,1,2,2,2,3,3,4,4,4`. The released switch mis-sizes reserved MT A and C. Skip unsupported types as whole packets, even when a continuation word resembles a supported header. First implement raw two-word preservation and typed handling for Note On/Off, absolute CC and channel Pitch Bend. Preserve an unknown MT 4 status in diagnostics on a UMP ingress. Give it an explicit unsupported outcome at a MIDI 1.0 conversion boundary. [UMP lengths and translation, Table 4 and Appendix D](https://amei.or.jp/midistandardcommittee/MIDI2.0/MIDI2.0-DOCS/M2-104-UM_v1-1-1_UMP_and_MIDI_2-0_Protocol_Specification.pdf)

For MCU feedback replay `40E70000 <u32>` as strip 8 bend (`u32 >>> 18`), and `40905E00 FFFF0000` as Play LED on. Decode the upper 16 velocity bits before reducing to seven (`velocity16 >>> 9` for the translated MCU LED fixtures). Test off, flash, solid and explicit Note Off. For ordinary translated CC extract `word1 >>> 25`; accept time digits CC 40–45 hex on channel 16 in MT 2 or MT 4. Verify identical MCU state from both formats and zero return traffic. Keep the original words for diagnostics and Generic high-resolution state.

**Egress policy.** Generic normalized Pitch Bend can originate a 32-bit value directly on a confirmed MIDI 2.0 route. Expose an explicit native-resolution absolute CC binding or send option that can be exercised from the Inspector on a normal fader (use CC 74 in fixtures). Old generic CC and paired-CC bindings retain their meaning. For MT 4 channel bend down-convert with `u32 >>> 18`, then send LSB followed by MSB. For ordinary absolute CC use `u32 >>> 25`. For up-conversion use the MIDI Association bit-scaling rules and official center/endpoints. Keep bank-select and RPN/NRPN sequences out of the ordinary-CC translator. Preserve MCU's MIDI 1.0 semantics on byte and MIDI 1.0 UMP routes. If a route requires MIDI 2.0-only protocol, use a verified translator for the needed message types or surface an unsupported MCU route.

**Bridge transition.** Add the v2 Kotlin entry points alongside the working v1 channel first. Switch Dart producer, consumer, both isolates, fallback path and diagnostics as one compatible Dart slice. Validate version, count, stride and MT before accessing a record. Keep timestamps in ns through timing comparisons, substitute the local monotonic clock for an unspecified timestamp, and convert units once for display. Use primitive arrays for queue slots and transfer complete batches. Test pooled-buffer ownership until channel serialization completes, overflow counters, and stale callback rejection after reconnect. Coalesce only continuous positions, preserve the latest final position and guarantee release ordering under the supported load.

Select the inbound batch version explicitly when Dart subscribes. In the v2 header carry the session generation and event count, and require precisely three used slots per event. Size validation must use the used extent of a pooled buffer. A v1 subscriber continues to receive its original pair format. Keep transport flags for `isFinal` and `acceptFeedback` independent of the unsigned value. Test a zero second word and `0xFFFFFFFF` on both sides of Android's signed integer boundary.

**State and normal entry points.** Use a bounded per-session/group buffer for active channel bend and high-resolution CC, dirty masks and one immutable frame update. Retain existing group-zero Generic providers. Key MCU feedback by selected port/group; unrelated devices can reuse the same channel and note numbers. Validate the public fader/Inspector → dispatcher → router → native sink path and the native callback → worker → selected control path.

### Phase 3 — surface, editor and template

1. **Mode and assignments.** Add a manual Generic/MCU selector in MIDI settings with Generic as the upgrade default. Persist the choice separately from `header_transport_assignments_v1`. Switching mode releases active gestures on their original route, clears old feedback and restores Generic assignments byte-for-byte. Keep ordinary generic controls usable on mixed layouts. Make an MCU-assigned control inactive in Generic mode. Have the gallery explain the required mode when the template is selected.
2. **Faders.** Wire `HybridTouchFader` to full-resolution values for initial state, live feedback, catch-up crossing and resume. Keep one touch owner per strip. Handle up, cancel, page change, rebind, background and disposal exactly once. Flush final position before release. On physical disconnect clear ownership locally and reject stale session events. Verify two fingers can write different strips independently and a host edit during a drag cannot take over the touched fader.
3. **Buttons and encoders.** Use momentary wire events even for host-latched Mute/Solo/Record. Keep local press appearance separate from authoritative host LEDs. Use a shared, visibility-aware clock for flashing. Route V-Pot deltas outside absolute CC feedback. Enable compatible MCU targets in `midi_action_fields.dart`, which currently preserves an existing MCU value but disallows selecting a new one.
4. **Original header.** Apply the role mapping to the existing drop-down 3×3 grid in `open_midi_screen.dart`. Preserve its layout and the Generic assignment editor. A tap must produce one press/release pair. Drive supported lamps from host feedback. Check narrow landscape, rotation and switching away with a button held.
5. **Template Gallery.** Add a distinct `PageTemplateId` for **MCU 8-Track Mixer** alongside the shipped generic mixer stub. Proposed geometry is nine columns and nine rows: eight V-Pots in row 0, four button rows in rows 1–4, eight track faders and master in rows 5–8. This gives 49 controls and uses the global header for transport. Test count, bounds, overlap, fresh IDs, stamp-fit failure, undo, export/import and restart. Verify touch targets on the Galaxy at supported zooms before finalizing geometry.

**Exit:** widget and integration tests cover normal editor creation as well as template creation, feedback echo, LED states and lifecycle releases. Re-run scaling, transport, Aftertouch, Latch Pad, note gate, legacy CC-pair and layout migration tests.

### 1. Carry SysEx7 through Android and Flutter

Extend `UmpPacket.kt`, the port-aware `MidiParser.kt` and the v0.5.0 bridge. Use one bounded assembler per open input and UMP group. On the byte-stream path collect between F0 and F7, forward interleaved system real-time independently, drop partial state on a new status that terminates SysEx, and process that status normally. For UMP MT 3, read the status/count nibbles, copy exactly the declared 0–6 seven-bit bytes, and omit padding and byte-stream delimiters. Emit one complete frame to the protocol worker. A short Start or Continue can still have a following packet. Serialize outbound fragments on their group so ordinary channel messages cannot split an open SysEx sequence. [M2-104, SysEx7 and interspersed messages](https://amei.or.jp/midistandardcommittee/MIDI2.0/MIDI2.0-DOCS/M2-104-UM_v1-1-1_UMP_and_MIDI_2-0_Protocol_Specification.pdf)

| Input, hexadecimal | Expected result |
| --- | --- |
| Byte stream `F0 7E 7F F8 06 01 F7` or UMP `30047E7F 06010000` | One universal inquiry with payload `7E 7F 06 01`. The byte-stream clock is handled by the existing real-time policy. |
| `30160000 66141200`, then `30324142 00000000` | One eight-byte payload `00 00 66 14 12 00 41 42`. The same frame encoded for a byte-stream destination gains exactly one F0 and one F7. |
| Orphan Continue/End, count 7, nested Start, out-of-range buffer slice, disconnect mid-frame | Count the failure, discard the invalid assembly and accept the next valid frame. Two ports or groups can interleave independently. |

Start with a proposed 512-byte payload buffer plus space for both byte-stream delimiters. Test the limit on both transports. Advertise only the verified receive limit using the CI specification's size convention. Use a monotonic inactivity deadline per incomplete assembly (initial test setting 500 ms). Bound total concurrent assemblies by active ports/groups and cap queued completed bytes. Flush promptly on reconnect or overflow. Deliver control frames through a typed side channel carrying session generation, group and sequence; retain order relative to layout feedback at mode transitions. Pool primitive data on sustained voice paths. API 35+ virtual UMP service behavior gets its own fixture. API 33/34 and the Samsung gadget retain byte-stream qualification. [Android MIDI API](https://developer.android.com/reference/android/media/midi/package-summary) · [Android virtual UMP service](https://developer.android.com/reference/android/media/midi/MidiUmpDeviceService)

### 4. Kotlin versus AMidi measurement and decision

**Question:** where does the Galaxy spend the tail of the touch-to-feedback interval under simultaneous fader, meter and metadata traffic? The existing parser targets in TESTING.md are microbenchmarks (p50 <0.05 ms, p95 <0.1 ms, p99 <0.2 ms). Establish an end-to-end baseline and agree a numerical user-visible budget before comparing implementations. [Project performance targets](../TESTING.md) · [Flutter profiling](https://docs.flutter.dev/tools/devtools/performance)

| Measurement | Method and controls |
| --- | --- |
| Instrument the stages | Use sequence IDs in test instrumentation. Measure input → Dart dispatch → platform enqueue → Kotlin write on Android; Windows arrival → immediate echo on a Windows clock; Android receive → state update → Flutter frame on Android. Keep raw monotonic units and route IDs. Subtract timestamps only within a verified common timebase. A timestamp's display resolution is independent of jitter. |
| Reproducible load | Baseline the tagged/reviewed Kotlin path in profile/release mode on the Galaxy. Keep OS build, refresh rate, USB role, endpoint, host backend, power/thermal state and diagnostic settings constant. Warm up, collect at least five comparable runs per condition. Test idle, one fader, two physical touches, generated eight-strip automation at 120 Hz, then the same load with meters and metadata. Keep an idle tail after disconnect. |
| Quantify impact | Count sent/received edges, lost/duplicated commands, final position per strip, queue depth, drops and coalesced positions. Report p50/p95/p99/max by stage and round trip, deadline misses, UI/raster frame durations, process CPU, allocations/GC and thermal throttling. Log sample counts and between-run variation. Use Flutter frame timings plus Perfetto scheduling/FrameTimeline where supported. [Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline) |
| Compare fairly | First isolate Dart/native batching and UI frame scheduling; the current sink can wait 16 ms before a nonfinal flush. If a missed budget traces to batching or rendering, fix that owner and repeat. If transport/bridge time still dominates, prototype AMidi behind the existing backend on the same opened endpoint and compare A/B runs in alternating order. Keep translation, rate limits, gestures and host fixture identical. |
| Native candidate | Java/Kotlin still discovers and opens the MidiDevice. Convert it with `AMidiDevice_fromJava`, verify default protocol, open native ports, use timestamped sends and bounded receives on a worker. Plan a wake/scheduling strategy that avoids a tight poll loop. Give one owner each native handle; stop and join the worker, close ports, release the device and reject callbacks from the old generation. A bounded primitive ring across FFI needs explicit producer/consumer ownership and memory ordering; use separate lanes or serialize producers if the path has multiple writers. [Android native MIDI guide](https://developer.android.com/ndk/guides/audio/midi) · [NDK AMidi functions and API levels](https://developer.android.com/ndk/reference/group/midi) |

**Decision:** keep Kotlin when it meets the agreed end-to-end budget or transport changes fall within repeated-run variation. Promote an optional AMidi backend only when its reproducible p95/p99 improvement addresses the attributed miss and preserves byte-stream/UMP parity, release ordering, recovery and thermal behavior. Retain Kotlin fallback when a port cannot use the native path. A negative benchmark result is a completed audit. Record traces, conditions, budgets and the decision for both physical USB MIDI 1.0 and any separately verified native UMP fixture.
